# Native pump and Window peer for actual WPF

`Wpf.Portable.NativeHost` connects the source-built WindowsBase dispatcher to a Linux X11/GLib event pump. It does not implement another WPF dispatcher or priority queue. The actual WPF dispatcher retains operation ordering, timers, cancellation, synchronization contexts, nested frames and shutdown.

Call `NativeDispatcherHost.InitializeForCurrentThread(AppBuilder.Configure<YourApplication>())` on the intended UI thread before constructing its first WPF `DispatcherObject` or obtaining `Dispatcher.CurrentDispatcher`. This configures Avalonia's GLib X11 backend, initializes its application and registers the thread-local WPF pump factory. Other WPF dispatcher threads retain their managed pump. This entry point supports the pinned Linux GLib backend only.

The adapter uses Avalonia 12.1.4's typed `[PrivateApi]` `Dispatcher.PlatformImpl` and `IControlledDispatcherImpl`. The package's own `AvaloniaAccessUnstablePrivateApis` build target permits those references without reflection. Its `AVA3001` maintenance warning remains visible. Packages and transitive content hashes are locked and startup rejects another native implementation or version. The package target compiles against its net8.0 implementation assemblies, which the .NET 10 host can load. A narrow [source-built X11 adaptation](Avalonia.X11/UPSTREAM.md) supplies access to the actual queued native input and guards the existing GLib Background callback. This is an explicit unstable dependency requiring review and regression tests before any Avalonia upgrade.

The supported public dispatcher surface alone was insufficient: `RunJobs` explicitly omits OS events and `MainLoop` exposes a whole loop rather than a bounded native iteration. The owned adapter uses the stable GLib C API for a single `g_main_context_iteration` on the same default context used by Avalonia's GLib X11 backend.

- `Wake` coalesces cross-thread notifications and calls `g_main_context_wakeup` without invoking WPF work.
- Each `WaitAndDispatch` first dispatches existing Xlib events through Avalonia's original event dispatcher and at most one event from its existing grouped input queue. It skips blocking when that path made native progress. `WaitAndDispatch(0)` never waits for a source. A positive timeout attaches a temporary monotonic GLib timeout source. `-1` may wait indefinitely until a native source or wake arrives. The timeout bounds waiting; callback execution and upstream native queue draining can take longer.
- Nested WPF frames may recursively iterate the same owner-thread GLib context. Avalonia's GLib X11 source explicitly permits recursion.
- The context is acquired on the owner thread and released during WPF pump disposal after native iterations unwind.
- Signal and Background callback exceptions are captured through Avalonia's external GLib exception logger and rethrown after the C callback boundary returns. One tracked upstream source guard is required for Background callbacks, which otherwise abort the process. Direct managed input-provider callbacks propagate directly to the WPF frame and are tested separately.

`HasPendingInput` checks both Avalonia's actual X11/grouped native event queue and `g_main_context_pending`. Avalonia reports `CanQueryPendingInput=false` for GLib because a narrow X11 query omits ready GLib sources. The additional GLib query is deliberately conservative: non-input ready work may defer WPF Input/Background work. The Windows WPF implementation similarly includes `QS_INPUT`, `QS_EVENT` and `QS_POSTMESSAGE`, but these source sets are not equivalent. Continuously ready foreign GLib sources could starve lower WPF priorities. The integration tests measure Background progress amid native key events and rendering; they do not establish arbitrary GTK integration or complete Win32 priority equivalence.

The native window and keyboard event target in `NativeDispatcherIntegration` are Avalonia objects. Actual WindowsBase dependency objects and dispatcher operations run beneath them. That fixture remains dispatcher-component evidence. The separate `NativeWindowIntegration` fixture exercises the genuine WPF Window, retained rendering, InputManager and controls described below.

For genuine WPF windows, call `NativeWindowHost.InitializeForCurrentThread(AppBuilder.Configure<YourApplication>())` instead of the dispatcher-only entry point. It selects the pinned CPU framebuffer backend, obtains real native XSETTINGS pointer preferences, registers the explicit `portable-light-v1` system profile and installs the true PF window factory. Registration precedes construction of WPF controls and the first settings read. It does not install an Avalonia control tree or convert WPF content to Avalonia controls.

The factory creates an initially hidden native `IWindowImpl` and an inert X11 input-root token without pumping or raising callbacks. The actual Window attaches its real source before showing. Window owns close cancellation and peer disposal; the source borrows the peer. A native close request always defers to Window policy. An accepted `Close` acknowledges once after low-level native disposal returns, including X11 destruction being requested. This is a synchronous disposal acknowledgement, not a server roundtrip guarantee. Failed disposal does not synthesize a successful close.

State, resize, position and scaling callbacks schedule one coalesced, lifetime-guarded real WPF Send operation. It reads a complete fresh metrics snapshot and publishes state and metrics after the upstream callback returns. The pinned X11 handlers continue using the native handle after these callbacks, so synchronous WPF StateChanged or DpiChanged handlers must not destroy it inside that continuation. Direct close from either event is tested with an unrelated native frame afterward. A confirmation can retry a newer pending application state once after the upstream callback returns; it does not create another queue or continually retry rejected requests. Native withdrawal while hidden preserves the last semantic visible/requested state rather than reporting a false WPF Normal transition. External maximize/minimize, immediate hide/show, rapid state changes and pending restore dimensions are exercised separately with workspace Openbox.

Each metrics publication queries actual client pixels, client screen origin, bounded native frame extents and state on the same X11 display/XID, then captures those values with DPI before either Source or Window receives the event. Client/outer sizes, desktop position and screen conversions use that snapshot. This avoids the pinned backend's delayed Configure job cache, which was observed reporting 318x175 while the same native connection reported 498x375. Queries do not pump events, grab the server or modify upstream caches. Explicit client-size requests use the pinned native resize body through the owned partial adapter so equality with a stale backend cache cannot suppress the request. The existing coalesced metrics operation acknowledges actual server geometry even when an unchanged request produces no native resize event.

The source's synchronous `Present` span contains premultiplied BGRA. The peer validates dimensions, stride and native surface format, clears the locked native viewport, copies the bounded overlapping rows and columns then releases the lock to invoke the original X11 blit. A valid source frame can describe the last processed metrics while a native Configure event is still queued; this transition clips or clears pixels until that real event schedules the correctly sized frame. Invalid dimensions, short buffers, narrow strides and unsupported native layouts still fail. It retains no caller memory. Native expose invalidates the real source; resize and scaling callbacks propagate client DIPs and uniform X11 DPI. A detached, disposed or closed source cannot present a stale frame. Independent per-axis screen DPI remains unqualified. Window-manager decoration/state behavior is exercised separately by the workspace Openbox fixture.

Native raw reports enter the actual source and WPF input provider. Logical key names map through real WPF `KeyInterop`; no Windows scan code is available, so reports carry scan code zero. Native key/mouse timestamps preserve their low 32-bit millisecond value; timestamp-free X11 focus notifications use the local tick count. Committed text supports BMP characters; surrogate text fails explicitly. Mouse positions are converted from native client DIPs back to physical client pixels. Focus changes, both sides of button/key transitions and capture loss are reported through the genuine pipeline. Pointer capture uses an actual X11 grab on the existing backend display. Native activation snapshots query XKB key state and an atomic XInput2 position/five-button bitmap. They do not fabricate held-key or button transitions. Hidden/disabled peers deactivate their input and ignore queued raw events until shown/enabled again. Horizontal wheel routing, touch and pen input fail explicitly outside the initial mouse contract.

This initial native profile requires both requested client extents to convert to at least one X11 pixel. Zero or subpixel requests throw a named managed unsupported diagnostic before size hints or configure requests. Supported one-pixel dimensions remain valid. Logical zero-size mapping and native minimum-size normalization need a future explicit contract; explicit requests are not clamped or acknowledged with invented geometry. An existing window's DPI transition preserves the legal one-pixel native minimum when conversion would otherwise truncate to zero; the original native resize path and actual server metrics acknowledge that geometry.

Native cursor shape and visibility are independent per-peer state. Changing a supported shape while hidden retains that shape while applying the transparent native cursor; showing restores the latest requested shape. The fixture queries the actual XFixes server cursor image to verify both transitions. Focus acquisition returns false for a non-viewable native window and leaves later window-manager focus delivery intact.

After native closure, cursor shape changes return false. A visibility restoration may acknowledge that destruction has already eliminated cursor ownership; it sends no command to a dead XID. The genuine source can therefore complete its cursor/capture cleanup after the peer's disposal acknowledgement.

X11's Avalonia `DBusPlatformSettings` inherits fixed mouse double-click defaults, so the Window entry point deliberately reads the actual `_XSETTINGS_S<screen>` selection owner's `_XSETTINGS_SETTINGS` property instead. Its bounded parser validates byte order, entry count, types, lengths, duplicate preferences and values. Missing native preferences fail by name. The [XSETTINGS registry](https://wiki.freedesktop.org/www/Specifications/XSettingsRegistry/) defines `Net/DoubleClickDistance` as a maximum pixel distance and `Net/DoubleClickTime` in milliseconds. The distance is supplied directly to the existing WPF physical-client delta comparison, with no factor of two. Colors and the initial 4-DIP horizontal/vertical drag thresholds remain an explicit portable product profile; those thresholds are not OS-detected preferences. Live desktop appearance parity is separate work.

The [native Window fixture](../../Tests/NativeWindowIntegration/README.md) uses actual XTest server injection and XGetImage readback on a dedicated Xvfb server. It supplies explicit genuine WPF control templates and declared test-owned XSETTINGS values. Its JSON must pass the requested Button, TextBox, retained pixel and modal cases before treating the Window integration gate as passed. Physical desktop qualification and default application theme compatibility remain separate gates.
